## 解决什么问题
接手老项目或准备重构时用：让 agent 读 Git 历史（大白话：代码每次修改的存档记录）、关键 PR（大白话：合并代码前的“修改申请”）和架构演变，分清哪些设计是故意的、哪些是历史遗留、哪些是为已经不存在的问题加的，找出能安全删掉的部分。

## Prompt
原文（卡兹克第 7 条）：
```text
深入分析整个代码库的 Git 历史、关键 PR 和架构演变过程。找出哪些设计是有意为之，哪些是历史遗留，哪些是为了解决已经不存在的问题而引入的。识别可以安全移除的历史包袱。
```

增强版（本库按评论区改进整理，非原文）：
```text
深入分析整个代码库的 Git 历史、关键 PR 和架构演变过程。找出哪些设计是有意为之，哪些是历史遗留，哪些是为了解决已经不存在的问题而引入的。
要求：
1. 每条判断都要对应到具体的 commit 或 PR（给出 hash / 编号）；找不到记录的，标为“推测”或“原因未知”，不要直接判成历史包袱。
2. 只列删除候选，不要动手删。候选列成表：原来挡什么坑、现在凭什么不用挡、对应的历史故障和回归测试是什么、删坏了怎么恢复。
3. 删之前先把这段代码当初修的那个 bug 找出来给我看。
```

## 已知坑 & 评论区改进（这一条评论区修正最多）
- “第 7 条我会再加一句：把判断依据对应到具体 commit 或 PR，找不到记录的就标为推测。否则‘历史包袱’太容易变成 AI 给自己没理解的设计编一个故事。”—— [@Talljackcv](https://x.com/Talljackcv/status/2122587408453812648)
- “找不到当初为什么这么写，就标‘原因未知’，别直接判成历史包袱。再让它把删除候选列成表：原来挡什么坑、现在凭什么不用挡、删坏了怎么恢复。”—— [@UncleJAI](https://x.com/UncleJAI/status/2122482064658518462)
- “删之前先找到对应的历史故障和回归测试。看起来像包袱的分支，有时正是替一个不再有人记得的边界条件兜底。”—— [@YXxquf](https://x.com/YXxquf/status/2122517185008672945)
- “Show me the bug this workaround originally fixed before deleting it.”—— [@AlexHu0110](https://x.com/AlexHu0110/status/2122300665859018851)
- “第7条里最贵的两个字是‘安全’。Git 里没写当年为什么绕路，不代表那堵墙已经拆了。”—— [@wangjun45108091](https://x.com/wangjun45108091/status/2122587394528751621)
- 真实翻车：“删掉一个看着没用的兼容层，第二天老用户就跑来问功能去哪了……那次之后我就不太敢让Agent自己判断什么叫包袱了。”—— [@spb_musketeer](https://x.com/spb_musketeer/status/2122555833951154497)
- 疑问：“它会不会把‘没人敢动的老代码’误判成有意设计？”—— [@0x5668_nft](https://x.com/0x5668_nft/status/2122539828902494625)
