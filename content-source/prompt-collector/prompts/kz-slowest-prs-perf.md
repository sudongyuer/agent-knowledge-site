## 解决什么问题
App 变卡、但不知道是哪次改动引起时用：让 agent 把最近一段时间的 PR 过一遍，揪出“最慢的”几个，看有没有导致卡顿、能优化的地方。

## Prompt
原文（卡兹克第 9 条，XX 是你自己填的天数）：
```text
全面分析最近XX天里的所有的PR，找出最慢的那几个，看看有没有导致卡顿、可以优化的地方。
```

增强版（本库按评论区整理，非原文）：
```text
全面分析最近 [N] 天里的所有 PR，找出“最慢”的那几个，看看有没有导致卡顿、可以优化的地方。
先说明你用什么指标定义“最慢”（例如：引入的运行时耗时变化、CI 构建时间、review 来回轮次），并且至少同时看两个指标。每个结论附上数据来源（性能测试结果、CI 日志、profile 截图或命令输出）；拿不到数据的标成“推测”。
```

## 已知坑 & 评论区改进
- 原文里“最慢”有歧义，要先定义口径：“最慢的PR，到底按什么算，review来回次数，还是CI跑完的时间。我之前按review轮次筛，筛出来全是需求扯皮的，真正拖时间的构建缓存问题反而漏了。后来改成两个数一起看才顺。”—— [@PlayAIwithRon](https://x.com/PlayAIwithRon/status/2122307699409027574)
- 本库注：原文的“卡顿”更像指运行时性能（App 卡），评论者理解成了 PR 流程慢。用之前想清楚你要查的是哪一种。
