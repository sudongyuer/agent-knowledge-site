这是一份补课清单：下面 8 个都是社区公认重要、但之前简报漏掉的东西，按「影响力 × 对你的实用程度」排序。star 数是今天（2026-11-17）从 GitHub 实际查到的。

## 1. Anthropic 官方插件市场：先装 Anthropic 自己做的几个

- **是什么**：[claude-plugins-official](https://github.com/anthropics/claude-plugins-official) 是 Anthropic 维护的 Claude Code 官方插件目录（47.5k star），今天查到收录了 317 个插件，Superpowers 也在里面。里面有一批是 Anthropic 自己写的，对你最有用的是这几个：
  - `feature-dev`：专门做新需求，分 7 个阶段：先弄清需求 → 派 2~3 个 subagent 并行读代码 → 把不清楚的地方列成问题，**等你回答** → 出 3 套方案（最小改动 / 最干净 / 折中）让你挑 → 再写代码和 review。正好回答你问的「新需求怎么开发」。
  - `frontend-design`：做 UI 时避开「一看就是 AI 做的」通用审美。
  - `skill-creator`：帮你写 skill，并测它到底有没有被正确触发。
  - `pr-review-toolkit`：一组专门的 review agent（注释、测试、错误处理、类型设计等）。
  - `claude-md-management`：体检 CLAUDE.md，把会话里学到的东西补进去。
- **为什么重要**：这是官方出品、官方维护，比社区的东西更稳，装起来也最省事。

```text
/plugin install feature-dev@claude-plugins-official
/plugin install frontend-design@claude-plugins-official
/plugin install skill-creator@claude-plugins-official
```

装好后可以用这个 prompt 试跑一个小需求：

```text
用 /feature-dev 帮我做一个小需求：<一句话描述需求>。

要求：
1. 每个阶段结束时停下来，给我看这个阶段的产出（需求理解、读过的关键文件列表及行号、待澄清问题、3 套方案对比），等我确认再进入下一阶段。
2. 在我选定方案、你准备写任何文件之前，先列出要新建/修改的文件清单，等我确认。
3. 验收标准：
   - 需求里的每一条都有对应的实现位置（文件:行号）；
   - 项目已有的类型检查、lint、相关测试全部通过；
   - 有至少一个新测试覆盖这次的主要行为。
4. 证据：贴出上面每条命令的原始输出（命令本身 + 结尾的通过/失败行），不要只说「已通过」。
5. 最后用 5 行以内总结：改了什么、没做什么、还有什么风险。
```

来源：[anthropics/claude-plugins-official](https://github.com/anthropics/claude-plugins-official)（Anthropic）；[feature-dev 说明](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/feature-dev)

## 2. Expo 官方 skills：直接对口你的 mobile 开发

- **是什么**：Expo 团队官方出的一套 agent skills（[expo/skills](https://github.com/expo/skills)，4.2k star），Claude 和 Codex 的官方插件市场都已收录。它教 agent 正确使用 Expo Router 导航、原生风格 UI、动画手势、设计系统 token、EAS 构建发布、SDK 升级等。其中 `expo-design-system` 还能做「设计系统漂移检查」，即找出代码里没按规范来的颜色、间距等。
- **为什么重要**：agent 写 RN/Expo 最常错的就是 API 用旧了、导航写法不对。官方 skill 把这些约束直接教给它。star 数不高，但对你来说是这份清单里最对口的一个。

```text
/plugin install expo@claude-plugins-official
```

装好后可以先让它审一遍现有页面：

```text
请先加载 expo-overview skill，再按它的指引选用合适的 Expo skill，帮我审查这个 Expo 项目里的一个页面：<页面路径或名称>。

要求：
1. 只读、不改：先列出这个页面和 Expo 官方推荐写法不一致的地方（导航、原生 UI、动画、主题 token 各一类），每条注明文件:行号，以及对应的是哪个 skill 里的哪条建议。
2. 每条标注「确定」或「推测」：能在 skill 原文或 Expo 文档里找到依据的算确定，并贴出依据原文；找不到的标为推测。
3. 按「改动小、收益大」排出前 3 条修改建议，每条写清楚改完后怎么验证（具体命令或在模拟器上看哪个画面）。
4. 我确认要改哪几条之前，不要写任何文件。
验收标准：每条问题都有文件:行号和依据；前 3 条建议都有可执行的验证方法。
```

来源：[expo/skills](https://github.com/expo/skills)（Expo 团队）；[Expo Skills 文档](https://docs.expo.dev/skills/)

## 3. gstack：Garry Tan 的「一人软件工厂」

- **是什么**：YC 总裁 Garry Tan 公开的 Claude Code 配置（[garrytan/gstack](https://github.com/garrytan/gstack)，141.9k star）。他在 README 里直接说这是「我每天在用的开源软件工厂」。它把 agent 分成虚拟团队里的不同角色：
  - `/office-hours`：像 CEO 一样质疑你的需求，写出设计文档；
  - `/plan-ceo-review`、`/plan-eng-review`：分别从产品和架构角度审计划；
  - `/review`：找「CI 能过但上线会坏」的 bug；
  - `/qa`：打开真浏览器点一遍，复现并修 bug；
  - `/ship`：跑测试、review、开 PR。
- **为什么重要**：它和你想搭的工厂几乎是同一个东西，而且是顶级创业圈的人每天在用。注意它装得比较深：会改 CLAUDE.md，还会注册 hooks，需要 Bun。建议先只试 `/office-hours` 和 `/review`。

安装（官方 README 的命令，装在用户目录 `~/.claude/skills/gstack`）：

```text
git clone --single-branch --depth 1 https://github.com/garrytan/gstack.git ~/.claude/skills/gstack && cd ~/.claude/skills/gstack && ./setup
```

试用 prompt：

```text
我想试用 gstack，但先别动我的项目。请：
1. 读 ~/.claude/skills/gstack 下的 README 和 setup 脚本，告诉我 setup 会写哪些文件、注册哪些 hooks、改不改 CLAUDE.md。逐条列出，并附上脚本里对应的行号作为证据。
2. 列完后停下，等我确认再运行 setup。
3. 装好后在一个新分支上，对一个我指定的小需求跑 /office-hours，把它写出的设计文档路径和前 20 行贴给我。
验收标准：第 1 步的清单每条都有行号证据；第 3 步产出的设计文档存在，且至少包含问题陈述、被质疑的假设、2 种以上做法这三块。
```

来源：[garrytan/gstack](https://github.com/garrytan/gstack)（Garry Tan）

## 4. Compound Engineering：让每次改动都让下次更容易

- **是什么**：Every 公司官方的插件（[EveryInc/compound-engineering-plugin](https://github.com/EveryInc/compound-engineering-plugin)，26.1k star），由 Kieran Klaassen 和 Trevin Chow 维护，含 38 个 skill。核心是一个 6 步循环：想清需求 → 写计划 → 实现 → 精简 → review → **沉淀**（`/ce-compound`）。最后一步把这次学到的东西写进 `docs/solutions/`，下次写计划时会自动读到。它的理念是「80% 时间花在计划和 review，20% 花在执行」。
- **为什么重要**：「compound」是复利的意思。这正是咱们说的「每个错误都编码进环境」，而且已经做成能直接用的工具。X 上有人用过 gstack、GSD、Superpowers 后说「最后总会回到 compound-engineering，因为它不臃肿」（[Jarod Taylor](https://x.com/jarodtaylor/status/2067655193370448346)，个人观点）。

```text
/plugin marketplace add EveryInc/compound-engineering-plugin
/plugin install compound-engineering
```

不装插件也能借鉴它的「沉淀」这一步：

```text
我们刚完成了一个任务。请做一次「复利沉淀」：
1. 回顾这次会话：列出踩过的坑、返工过的地方、我纠正过你的地方。每条都引用会话里的原话或具体的命令输出作为证据，找不到证据的不要写。
2. 每条判断属于哪类：需求没说清 / 缺验收标准 / 忽略了项目约定 / 工具或环境问题 / 其他。
3. 对重复可能再犯的条目，起草一条可复用的规则，并建议放在哪：项目的 docs/solutions/<主题>.md、CLAUDE.md 或 AGENTS.md 的某一节，或者做成一条自动检查（lint 规则、测试或 hook）。
4. 先把草稿和目标路径给我看，我确认后再写文件。
验收标准：至少产出 1 条落到文件或自动检查里的规则；每条规则写清楚「什么情况下触发、要怎么做、怎么检查做没做到」。
```

来源：[EveryInc/compound-engineering-plugin](https://github.com/EveryInc/compound-engineering-plugin)（Kieran Klaassen、Trevin Chow / Every）

## 5. DESIGN.md：把设计规范写成 agent 读得懂的文件

- **是什么**：Google Labs 提出的一种文件格式（[google-labs-code/design.md](https://github.com/google-labs-code/design.md)，28.9k star）。一份 DESIGN.md 分两层：上面是机器能精确读的设计 token（颜色、字体、圆角、间距、组件），下面是大白话写的设计理由。它还带检查工具，能找出坏掉的 token 引用、对比度不达 WCAG 标准的地方，以及两版之间的差异。配套的 [VoltAgent/awesome-design-md](https://github.com/VoltAgent/awesome-design-md)（127.9k star）收集了很多知名品牌设计系统的 DESIGN.md，可以直接拿来参考。
- **为什么重要**：这是「把品味交给 agent」最具体的做法，正好对应你关心的 UI/UX。注意规范版本目前还是 alpha。

```text
请为当前项目起草一份 DESIGN.md，格式按 https://github.com/google-labs-code/design.md 的规范（YAML token + markdown 说明）。
1. 先只读：从代码里实际找出现有的颜色、字体、间距、圆角、主要组件样式（主题文件、样式常量、组件库配置等），每个 token 注明来源文件:行号。代码里不一致的（比如同一种灰用了 3 个色值）单独列出来，不要自己统一。
2. 把草稿和「不一致清单」先给我看，我确认后再写 DESIGN.md 文件。
3. 写完后运行 npx @google/design.md lint DESIGN.md，贴出完整 JSON 输出。
验收标准：每个 token 都能追溯到代码位置；lint 没有 error；所有对比度 warning 都列出来，并附一句修改建议。
```

来源：[google-labs-code/design.md](https://github.com/google-labs-code/design.md)（Google Labs）；[VoltAgent/awesome-design-md](https://github.com/VoltAgent/awesome-design-md)（VoltAgent）

## 6. mobile-mcp：让 agent 自己操作模拟器、看真 app

- **是什么**：一个 MCP 服务（[mobile-next/mobile-mcp](https://github.com/mobile-next/mobile-mcp)，10.6k star），让 agent 能操作 iOS 和 Android 的模拟器、真机：读界面结构、截图、点击、输入。官方插件市场里还有一个 `xcode` 插件，能构建和运行 Xcode 工程、驱动模拟器、读构建日志。
- **为什么重要**：「agent 看得到真产品」是领先团队的第一条共性。网页有浏览器工具，移动端靠的就是这类工具。有了它，agent 改完 UI 能自己在模拟器里点一遍、截图给你看，不用你手动验收。

```text
claude mcp add mobile-mcp -- npx -y @mobilenext/mobile-mcp@latest
```

试用 prompt：

```text
用 mobile-mcp 帮我在模拟器里验收一个 UI 改动：<描述改动和入口页面>。
1. 动手前先告诉我你会启动哪个模拟器、会点哪些步骤，等我确认。
2. 按步骤操作：进入页面 → 截图 → 走一遍主要交互（点击、输入、返回）→ 每一步截图。
3. 对照需求逐条检查：文案、布局、空状态、错误状态、返回后的状态是否正确。
4. 证据：每条检查结论都要对应一张截图（给出截图路径）或界面结构片段；看不出来的标「无法验证」，不要猜。
验收标准：需求每一条都有「通过 / 不通过 / 无法验证」的结论和证据；不通过的给出复现步骤。整个过程不修改任何代码。
```

来源：[mobile-next/mobile-mcp](https://github.com/mobile-next/mobile-mcp)（Mobile Next）

## 7. Addy Osmani 的 agent-skills：从需求到上线的整套工程 skill

- **是什么**：Addy Osmani 的 [agent-skills](https://github.com/addyosmani/agent-skills)（118.5k star），把资深工程师的流程拆成 25 个 skill 和 9 个命令，覆盖定义 → 计划 → 实现 → 验证 → review → 上线，对应 `/spec` `/plan` `/build` `/test` `/review` `/ship` 等。`/build auto` 是你批准一次计划后，它自动把所有任务做完；但每个任务仍然先写测试、单独提交，遇到失败或高风险步骤会停下来。
- **为什么重要**：和 Superpowers、gstack 是同一类东西（X 上常被放在一起比较）。不过它可以按需只装单个 skill，比如只装「一次问一个问题、把需求问清楚」的 `interview-me`，比整套装上更轻。

```text
npx skills add addyosmani/agent-skills --list
npx skills add addyosmani/agent-skills --skill interview-me
```

来源：[addyosmani/agent-skills](https://github.com/addyosmani/agent-skills)（Addy Osmani）

## 8. Spec Kit / OpenSpec：规格驱动开发的两个主流工具

- **是什么**：11-05 的今日概念讲过「规格驱动开发（SDD）」，意思是先写清楚规格再让 agent 写代码。但当时没介绍落地工具。最主流的两个：
  - GitHub 官方的 [Spec Kit](https://github.com/github/spec-kit)（150.2k star）：一串命令走完 原则 → 规格 → 计划 → 任务 → 实现，另有修 bug、评估想法的流程。
  - [OpenSpec](https://github.com/Fission-AI/OpenSpec)（75.1k star）：更轻，适合在已有项目里逐个提「变更提案」。
- **为什么重要**：在你的工厂里，需求进来后的第一步就是变成 agent 能照着做的规格，这两个是现成的模板。

```text
请帮我评估 Spec Kit（https://github.com/github/spec-kit）和 OpenSpec（https://github.com/Fission-AI/OpenSpec）哪个更适合当前项目。
1. 读两者的 README 和文档，各总结：工作流的步骤、会在仓库里生成哪些文件和目录、适合新项目还是已有项目。每条附原文链接或引用原句作为证据。
2. 结合当前项目的实际情况（先读目录结构和现有的 CLAUDE.md / AGENTS.md），给出推荐和理由。
3. 用一个我指定的小需求，只在对话里演示推荐工具会产出的规格文档长什么样，不要真的初始化。
4. 我确认后，才允许在新分支上运行 init 并写入文件。
验收标准：对比表每格都有出处；演示的规格包含目标、非目标、验收标准三部分。
```

来源：[github/spec-kit](https://github.com/github/spec-kit)（GitHub）；[Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)（Fission AI）
